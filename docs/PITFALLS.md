# 技术陷阱

## 命令记录器不能与被执行程序共用报告文件名

**Verified**：2026-11-06清理程序成功写出详细`cleanup.json`后，同目录的命令记录器也用label`cleanup`写`cleanup.json`，覆盖了前者；后续读取`state`字段因此报错。删除已成功完成，不应因此重复删除或假称完整报告仍在。保留原样命令输出和实际脚本，汇总只从真实stdout恢复；归档CRC、原盘/新盘hash、ISO数量及玩家安装文件另行复核。

修正为命令日志统一`stage-<label>.json`，程序结构化结果分别为`storage-report.json`、`post-clean-state.json`等。清理后的复核通过；缺失的详细逐文件hash报告没有被伪造重建。生成证据与执行记录必须分开命名。

## Windows发布目录与校验进程必须串行

**Verified**：e97f发布时，普通`Move-Item`遇到正在读旧目录的校验进程后失败，但此前已经移动了差分ZIP和字体预览两个子文件，不能把失败视为“完全没移动”。先按旧ZIP已知hash及未改字体预览hash恢复这两个文件，恢复原交付目录，再重试。

发布同卷目录应在全部读者退出后进行。源/目标绝对路径须位于明确build工作区，拒绝reparse项/越界子项，目标须不存在；采用`[IO.Directory]::Move(source,target)`的同卷目录重命名，并对已完成的目录重命名逆序恢复。不要在更换镜像目录的同时启动对该目录的验证。新目录发布成功后再串行执行修改版、独立副本回滚和恢复基线检查。此修正不修改游戏数据。

## e97f：完整RGB修底仍可能继承旧alpha，局部字床会留下材质矩形

**Verified offline**：旧无字床的decoded alpha仍有209/207/205等变化。仅换RGB或让最近色量化自由选择alpha，不能证明已清除旧字透明度结构。新指定腔体以可选`palette_constraints`限制原CLUT候选，使用`clear_regions`的可选`min_alpha`/既有`max_alpha`验证；不改CLUT，不把此策略强加给其他图片。非腔体端帽必须按原多边形排除，否则整矩形会吃掉三角端帽。

门板只换小字床，即使文字全新，也会因材质清晰度/灯光不同形成矩形补丁。实验室改为完整物理钢板面，原硬件/灯通过零覆盖孔保留；控制室顶部过渡在旧字和新字之外，不能混回旧字。生成稿添加的长横线并非原图结构，已明确否定，不把它当作背景保留。

**Verified offline**：等宽等高检查不会发现整词偏移。两态可声明原UV的`center_twice`及半像素容差；原生帧/端帽/灯与接缝另外按原索引验证。生成模型两次改成繁体或产生噪点的字稿均未采用；普通构建不依赖这些创作尝试。

## 17e7：无字供体自身有暗纹，半透明主图不能整床复制

**Verified**：e004所用“无字”玻璃供体仍画出了字母状的机械暗纹。即使完整内床已写入ISO，仍未满足玩家的去残留要求；不能再拿扩大矩形、旧样本改变或hash一致充当画面干净的证明。新供体须先独立查看、排除伪字纹，再注册到原端帽/框之间。

将已认可39号的半透明整块字床复制到40号不透明调色板，会出现暗矩形，虽然文字位置完全相同。该尝试已否定：只连续反解完整字形覆盖，在目标自己的红色底材上合成，不把主图的背景alpha带入不透明变体。

原“错误”后的光标不止此前登记的5×2片段，漏掉的上沿/右缘已经能红灯复现。按完整8×5原区域恢复。共同字号不等于相同阈值字面包围盒：重做页脚使用共同11px轮廓字格，145阈值字面核心为9/10px，不能通过二值加粗来伪造相等。

CLUT16图不能交给现有CLUT32高清键生成器：其显式拒绝为正确版本防线，不是应绕过的构建错误。相应图片先完成原生修订，高清目录不写猜测键。

原CLUT可以有多个RGBA完全相同的索引。只保护“未改的原图索引”还不够：对已汉化图再次导入时，93号主海报出现337处同色索引别名重选，解码画面不变，但违反主海报原字节保持。导入器新增可选、精确hash绑定的`reference`，仅在允许区域、量化后RGBA完全相同时优先保留前版索引；头/CLUT不符直接拒绝，不扩大修改区域。`reference_rectangles`进一步区分“保留已认可前版”的主海报与“恢复原索引”的侧边微字；整床偏好前版别名会反过来破坏后者的源指纹。默认导入和渲染颜色不变，新增五个合成回归。

**Verified**：此前将52块按钮机械材质当成旧字、要求全部改变，造成过度涂抹。最新意见明确要求恢复这些原细节；回归规则现区分 `preserved` 与 `changed`，历史预期和修正原因仍有记录。12块真正的EXIT旧字边缘继续要求改变。

**Verified**：透明主图的 alpha0 隐藏RGB不能直接量化到不透明CLUT，否则黑色/原英文会被重新显现。跨变体先在目标原材质上合成，保持新字形alpha，再量化；不把原英文逐像素alpha套回去。背景修复也不硬阈值裁切后撑大汉字。详见[IMAGE_FEEDBACK_C7.md](IMAGE_FEEDBACK_C7.md)。

## “中央文字区”并不等于完整按钮内底（历史方法，c7纠正材质分类）

**Verified**：主菜单完整内底修复后，L001_006/L001_007 的旧72×20中央修复仍漏掉26个按钮两端的字形状暗纹，52块样本与原盘完全相同。六张EXIT变体的旧核心掩码也漏掉上沿/右沿12块样本。此类原像素相同既不说明汉化未写入，也不说明符合无残留要求。

当前采用完整内底/完整旧字区恢复，保留已采用前景字稿，不再次用二值粗块字体代替。完整无字底纹须先单独查看，再查看叠字后原生图和最终ISO；64个源样本回归检查与逐图复核并用。详见ARTWORK_SWEEP。

Windows 创作辅助脚本写 JSON 应显式 LF，避免工作区与 Git 归档的换行规范不一致。本次八份像素差分规范换行后重新构建，11件核心输出逐字节相同，确认语义和成品未变；不通过手改最终清单来宣称可复现。

## START 只擦字心会留下完整旧光晕轮廓

**Verified**：旧版 `L001_004` 的 `[8,229,190,26]` 修改范围漏掉原英文在 y225..228 的红色光晕；即使成稿和 ISO hash 一致，外缘仍不干净。旧图四个拟清空槽边中，仅上沿就有 781 个非透明像素。现在完整精灵范围 `[0,225,214,31]` 替换为新原风格字形的 alpha，不拷贝旧字 alpha；四边 `clear_regions` 要求零 alpha，并独立从最终 ISO 检查。查看 RGBA 的隐藏 RGB 或只合成黑色底会误判，复查使用棋盘/明暗背景及原生 alpha。

## PNACH 在生成目录不代表模拟器已经安装

**Verified**：此次反馈时用户目录中没有本游戏 PNACH，模拟器日志明确显示没有找到/开启补丁；程序目录也不是该实例的用户数据目录。显式安装器读取现有 Folders 设置再复制源绑定文件，只创建本 CRC 的游戏配置，不改全局设置或其他游戏。用户手动运行的既有日志仅作诊断输入，工具仍不启动游戏。

## 登记数量不是全盘覆盖

**Verified**：此前“136 张目标图全部安装”的结论只对登记清单成立，仍漏掉原盘同名、调色、`_C`、破损及场景变体。现把 1140 个源 hash/2634 个引用的审查分类与 187 张安装清单分开，构建重扫全盘并验证成员名家族闭包。不同 CLUT、UV、照明或玻璃破损状态不能整图互相覆盖。

## 只擦亮色笔画或复用原 alpha 会留下旧字

**Verified**：旧按钮文字床及亮色遮罩没有覆盖所有暗描边；复用原带文字 alpha 又会把旧轮廓带回来。现在重建完整旧字区域、注册原生 UV/材质 alpha，字区外和 CLUT 保持。状态测量须排除胶囊自身金属亮边，否则把边框/光斑误判成字号变化。加载模糊帧不可按整个光晕单独缩放；应比较汉字核心和共同字格，保留原动效。

## 行首标点不只来自译文中的显式换行

**Verified**：原 RenderString 的 lookahead 只认 ASCII，中文自动折行能把句号单独放到下一行。译文手工断行修补不能代替字码级修复。独立验证又检出了四页文档的行首进度省略号和网络主机名的右引号；这些显式排版已修订。`%s` 等格式参数不是字面百分号，校验必须识别技术 token，不能为通过检查删掉参数。

## 不能照抄宽屏文件名，也不能假称实际运行通过

**Verified**：上游补丁文件名使用 `83B9AE36`，本盘原 ELF 的 PCSX2 XOR 结果却是 `2383B74A`；同一序列号不代表同一 CRC。三处原指令逐条一致后才采用该组数值；中文文本与 lookahead 又改变 CRC，必须按实际构建命名。CRC 算法不是 CRC-32。右摇杆、弹药、生命只以源指令与隔离夹具证明预期差分；不把存储 NOP、数学夹具或贴图读回说成模拟器执行/通关验收。

## 暗字识读不交给生成器补全

**Verified**：G376 曾被低对比预览误读，回到原生像素做仅供分析的增益观察后锁定为 `FRAGILE`，最终采用“易碎”。辨读与美术编辑分开；模糊微字不凭上下文发明正文。分析放大的图和被否定生成稿不参加构建。

## 只改道具显示名会破坏关联

**Verified**：同一道具在ITEM、EVENT、VAMPIRE、DOCUMENT、场景SCR/SCN和ELF中被引用。上游历史记录中有取得/掉落失效；本地原始引用表也验证了这些连接。默认把NAME归为`display_identifier`而不是普通正文；在完整引用组和容量审计前不改名。

## 英文文档不是原文逐偏移对照

**Verified**：原文DOCUMENT.SCR有92个TEXT，英文版有107个，虽然总payload长度相同，字段偏移已经变化。按ITEM块配对，不按相同字节位置配对后半文档。两份文档原版分别完全镜像，必须同步生成。

## 不按模板猜二进制文本

**Verified**：原ELF带大量DWARF调试数据，任意CP949扫描会把地址字节误认成韩文。正式构建只用固定版本的显式槽配方与完整原字节校验；`candidate_display`仅供继续审查，不意味着已确认可显示或可写。

## 字库页顺序与字码顺序相反

**Verified**：FONT_8含ASCII，FONT_1含最后一组韩文。必须按FNT中的纹理哈希定位。修改纹理名索引推断出的页会写错字形。

## 2539条上限写在查找指令里

**Verified**：只扩FONT.FNT不会扩展字形搜索。当前复用原双字节槽，保留ASCII/FNT/metrics；全量字符超2444时需要另行研究，不静默丢字。部分汉化还要保留尚在使用的原字码，例如本版`A4F6`。

## 13px直接hinting可能挤出14像素

**Verified**：所选字体部分字在直接13px raster时超过13行。现用4倍超采样后缩小，并沿共同基线放置；拒绝越界，不截掉底部。句号等标点不逐字垂直居中。此方法的游戏内观感仍待验收。

## 格式标记不是句中标点

`%s`、`%d`、`<O>`、`<BR>`不是自然语言标点，不能因此给无标点的系统句补句号。《诡秘之夜》的系统/道具规则由locale配置驱动；剧情正常使用句号。问号与感叹号不删。

## 修改副本与回滚副本必须分开

**Verified**：构建与应用都拒绝覆盖输入或已有输出。回滚测试在另一个已修改副本上执行，检查恢复全盘SHA，仍保留供玩家测试的修改镜像。差分是本项目MNP ZIP格式，不应交给xdelta工具。

## REA分析配置不等于所有平台都可反编译

本次Windows分析配置未完成MIPS ELF反编译。改用原ELF的DWARF1范围与独立指令读取核对，保存可重放的机器字节锚点；没有把工具失败写成反编译成功或运行成功。

## 输出事务与重复字段

构建/提取先在新临时目录完成，再发布最终目录；已有输出拒绝覆盖。脚本外层ID不同却指向同一物理字段时也须拒绝，不能让字典静默保留最后一条。printf检查覆盖星号宽度/精度、长整型和`%n`，新增占位符必须报错。

## 文档镜像声明不能是可选项

**Verified**：只在`mirrored_resources`非空时校验，会让删除该字段/改为空数组的文档仅回填一份。现对活跃DOCUMENT译文强制镜像，并在构建前核对原始模板；缺失、置空和未知目标都有拒绝测试。

## 原文/英译的专名和剧情并非逐句等价

**Verified 源文本**：英文武器Slayer/Reaper等不是韩文等级名的直译；“吸血鬼计划”与“远古计划”在英文部分内容被混写；팔마타原文为第三DNA名，而非已证实的植物叶片。按原文建立名词表，不凭英文改写推导未出现的设定。

## 主程序编码不能覆盖网络模块

**Verified**：NETGUICD.ELF中的已发现网络设置韩文为UTF-8，独立KOREAN.PF字体；主程序和RES脚本为CP949/映射字码。候选提取不意味着可用主程序回填器修改该模块。

## 字节出现不等于字形引用

**Verified 扫描结果**：几何/动画等二进制任意字节对会命中全部2444个双字节槽，即使要求可打印NUL串仍有大量误报。字体保护报告区分完整明文、ELF字符串候选、未知二进制巧合；候选未命中也不当成动态路径的全局空闲证明。

## 全文字集的分号下伸部

**Verified**：13px、4倍超采样时，本作全量目标字集的最高字形top=-46、全角`；`bottom=9，联合高度55大于52个超采样像素；构建曾以`outline glyph exceeds existing cell: '；'`退出。全文配置改为12px，共同基线平移-1个超采样像素即可容纳全套轮廓。原13×14槽/13×13可见区不变，不裁分号、不单独抬高标点。回归测试覆盖共同上下界冲突和上下平移。

## 哈希校验后重新打开字体路径

**Verified 合成复现**：先读取字体bytes计算hash、随后让fontTools/Pillow重新打开同一路径，文件若在两次读取间变化，记录的hash会与实际绘制来源不符。两个生成器现在都从同一份已校验的`BytesIO`读取；测试在校验后替换磁盘文件，输出仍与原字体构建逐字节一致。

## 尖括号不全是控制码

文档中的`<Skip>`与`<GATE OPEN>`是实际显示文本。处理链的精确静态证据及逐字段白名单见`TECHNICAL.md`。修复采用原盘hash/字段ID/源hash绑定，而非全局忽略未知标签；真正的按键、换行、printf顺序仍强制保留。

## 图片只擦亮字会留下暗边

原 UI 字体包含暗描边、投影、发光及 alpha 字层。按亮度选白色/金色笔画再覆盖会留下旧英文黑色轮廓；原生分辨率复查及用户反馈确认此失败。菜单应完整重建旧文字底纹，透明字层须连同旧光晕清除，再导入重绘字形。保持原调色板，预览必须从最终 TIM2 回读，不能用高分辨率生成图冒充交付。黑/红方块遮盖及默认普通字体直贴已被用户否定，source-style-only 配方禁止退回此路径。

## 暗淡状态与生成背景不是无用像素

**Verified**：U317 底部四条 OK/BACK 状态图使用近似常量灰色 RGB，字形主要在 alpha 中；直接查看 RGB 会误判成空白／灰块。黑底合成能看到暗淡／模糊文字，汉化需同时覆盖这些状态，不删除其图层。U548/U549 的原字是扁平青色，生成的浮雕／发光版本应丢弃而非直接缩小安装。

生成模型可能改变房间、控制器、图标或底纹几何，完整生成图不应替换原图。U555 的照片分别与原 U552/U554/U551/U553 四个象限对应，原无字照片可用于局部修复；其内部亮度关系为修复时的高置信度近似，不标成逐像素原背景复原。修改范围仍以显式文字区约束，其外原图与 CLUT 逐字节保持。

## 场景字层、霓虹边缘与斜排标题

**Verified**：G341 顶部字样的原 CLUT alpha 携带旧字覆盖率。把原像素 alpha 直接套回新汉字，会重新显出旧英文轮廓，并截断新字。黑底创作稿须按原 CLUT 的预乘 RGB 重新匹配索引，不能沿用旧字的逐像素 alpha；头部、调色板和文字区外索引仍保持。

ST0405_06 的霓虹光晕超出亮笔画；分别裁两条小矩形会留下接缝。使用包含完整旧光晕的共同编辑区，匹配原暗屏底色，并从最终 TIM2 复查。G104 的红色条带需保留原亮度和状态 alpha，生成稿的色漂不能作为新底板安装。

GALLERY_03 的斜排副标题大外接矩形包住 MN 徽记；直接贴回整个矩形会误改徽记。使用逐行窄带限定斜排字床，覆盖完整旧字而不是只擦亮色笔画。模型把金色字误画成金底黑字的 G341 稿已否定；最终采用原金色笔画/暗青字，不安装新底板。

## 高亮字形掩码混入按钮框 — Verified

# 当前运行反馈的新陷阱

- 全盘源 hash/引用登记闭合，不代表每项可读文字都已识别。`ST0101_042` 等嵌入名称不会被 `Gxxx/_C` 闭包捕获；明确视觉关联也要独立绑定源 hash/CLUT/偏移，不能只抄 donor 键。
- 给旧不透明字块补上更高的新字床，仍会留下中间旧材质与横向贴片边界。使用真实 alpha 的完整字稿与一层连续母材；内腔接边按原端帽轮廓，不用硬中央矩形。
- UV 中心不等于存储区中心。橙床左移后旧尾列也必须恢复；只把新前景放正不能清除旧覆盖。
- 主菜单画廊原生亮面阈值可因 CLUT/阴影量化偏 1px；HD 主体 alpha 证明横向中心精确。不能为了让某个颜色选择器过关而错误移动原本居中的高清字面。
- 未使用 atlas 区仍可能有旧暗影；FNT gutter 则会实际参与边缘过滤。分别检查 UV 内字面、UV 外留白和完整旧覆盖范围，不混称一种问题。
- 过场 `GetToken` 按 CRLF 读整行；去掉所有换行会破坏原生解析，即使 Python 分词检查相同也错误。保留命令行顺序、512 字节行缓冲、同尺寸输出和帧边界。
- ASR 对音乐/特效的“感谢观看／订阅”等输出不可当台词。未听审或无结束帧的草稿拒绝启用；不把 VAD 空结果当作已证实无对白。
